# Реестр источников

## Что такое источник

Источник — это **наблюдаемый** канал, за которым мы следим, чтобы находить:

- инфоповоды;
- темы для контента;
- рыночные сигналы;
- аргументы и возражения;
- истории и отзывы;
- идеи для сценариев общения.

Источник — это **не база знаний** и **не источник гарантированной истины**.
Публикации источника не копируются как готовый контент. На их основе создаётся
новый материал, который затем проходит обычную ручную проверку владельцем
(включая Safety Layer, если тема касается дохода, цен, скидок, тарифов, оплаты,
бронирования или доступности).

## Кто владелец реестра

**Control Center — владелец списка источников.** Здесь решается, какие источники
существуют и какие из них разрешены к использованию.

Travel Lead Radar в будущем станет только исполнителем: возьмёт активные
источники, посмотрит, для каких платформ у него есть сборщик, соберёт
публикации и сложит результат в свою `leads.db`.

> **Сейчас Radar ЕЩЁ НЕ читает этот файл.** Он продолжает работать со своим
> `app/sources/sources.json`. Переключение — отдельный следующий этап.

## Четыре разных состояния — не путать

Это самое важное место документа. Запись в реестре ≠ работающий мониторинг.

| Состояние | Что означает | Где проверяется | Сейчас |
|---|---|---|---|
| **Зарегистрирован** | Источник описан в `config/sources.json` | `load_registry().all()` | 24 источника |
| **Активен** (`enabled`) | **Разрешение** использовать источник | `registry.enabled()`, `collection_targets()` | 18 из 24 |
| **Есть сборщик** | Реализовано чтение этой платформы | `IMPLEMENTED_COLLECTOR_PLATFORMS` | в этом репозитории **пусто** |
| **Реально мониторится** | Источник физически читается | Travel Lead Radar, по своему файлу | 16 (через файл Radar, не через этот реестр) |

Ключевое различие: `enabled` — это **разрешение**, а не факт. Активный источник
на платформе без сборщика просто не будет собираться. Реальный мониторинг
требует и разрешения, и сборщика для его платформы.

`collection_targets()` возвращает **список намерения**: «за этим мы хотим
наблюдать». Это не отчёт о том, что уже собирается.

## Где хранятся источники

Единственное место — data-файл:

```
config/sources.json
```

Конкретные каналы **не зашиты** в Python. Чтобы добавить, отключить или
переименовать источник, правится только этот файл.

## Формат записи

Файл начинается с версии формата:

```json
{
  "schema_version": 2,
  "sources": [ ... ]
}
```

`schema_version` нужен, чтобы старый код не пытался прочитать файл нового
формата.

| Версия | Что означает |
|---|---|
| `1` | Базовый формат, блока `collector` нет |
| `2` | Добавлен необязательный `collector` (текущая версия) |

Обе версии читаются. Файл v1 остаётся валидным — у его источников просто
пустой `collector`. Неизвестная версия отклоняется с понятной ошибкой вместо
тихой неверной загрузки. Отсутствие поля трактуется как версия `1`. Блок
`collector` в файле, помеченном как v1, тоже отклоняется: иначе настройки
сборщика потерялись бы незаметно.

Сама запись источника:

```json
{
  "id": "telegram_example",
  "name": "@example",
  "platform": "telegram",
  "username": "example",
  "url": "https://t.me/example",
  "source_type": "monitored_source",
  "purpose": "content_and_business_signals",
  "enabled": true,
  "priority": 50,
  "notes": "Свободный комментарий",
  "collector": { "fetch_limit": 3 }
}
```

| Поле | Обязательно | Описание |
|---|---|---|
| `id` | да | Уникальный технический идентификатор |
| `name` | да | Человекочитаемое имя |
| `platform` | да | `telegram`, `vk`, `rss`, `web` — список расширяемый |
| `url` / `username` | да (одно из) | Адрес источника |
| `source_type` | да | Категория/роль: `monitored_source`, `community_comments`, `reviews_and_stories`, `own_web_resource`, … |
| `purpose` | да | Для чего наблюдаем источник |
| `enabled` | нет (по умолчанию `true`) | Разрешение использовать источник. `false` — в сбор не попадает никогда |
| `priority` | нет (по умолчанию `50`) | Меньше число — выше приоритет |
| `notes` | нет | Заметки |
| `collector` | нет (с v2) | Настройки конкретного сборщика — см. ниже |

### `platform` и `source_type` — разные вещи

Это место, где легко ошибиться при миграции. В Travel Lead Radar поле с именем
`source_type` означает **платформу** (`rss`/`vk`/`telegram`). В Control Center
это не так:

| Смысл | Control Center | Travel Lead Radar |
|---|---|---|
| Платформа | `platform` | `source_type` |
| Роль источника | `source_type` | — |
| Режим анализа | `collector.analysis_profile` | `analysis_profile` |

Значение Radar `source_type` переносится в `platform`, а **не** в одноимённое
поле Control Center. `analysis_profile` (`publisher` / `user_comment`) хранится
как настройка сборщика и никогда не маскируется под `source_type`.

### Блок `collector`

Всё, что нужно только конкретному сборщику, живёт отдельно от общих свойств
источника:

```json
"collector": {
  "analysis_profile": "user_comment",
  "posts_enabled": false,
  "comments_enabled": true,
  "vk_screen_name": "example",
  "vk_group_id": null,
  "fetch_limit": 3,
  "min_score_for_llm": 70,
  "language": "ru"
}
```

Реестр **не толкует смысл** этих настроек — он только проверяет типы известных
ключей, чтобы поле не поменяло смысл молча (строка `"false"` в булевом флаге
дала бы `True` и включила сбор там, где его выключали). Неизвестные ключи
сохраняются нетронутыми: их поймёт сборщик своей платформы.

| Ключ | Тип | Смысл |
|---|---|---|
| `analysis_profile` | строка | `publisher` или `user_comment` |
| `posts_enabled` | булев | Собирать посты сообщества |
| `comments_enabled` | булев | Собирать публичные комментарии |
| `drop_promo` | булев | Отбрасывать промо-посты (Telegram) |
| `fetch_limit` | число ≥ 0 | Сколько свежих публикаций брать |
| `min_score_for_llm` | число ≥ 0 | Порог передачи в LLM-анализ |
| `vk_screen_name` | строка | Короткое имя VK-сообщества |
| `vk_group_id` | число или `null` | Числовой ID VK-сообщества |
| `language` | строка | Язык источника (Radar печатает его в консоли) |

`enabled` и `collector.posts_enabled` — **разные вещи**. Первое разрешает
использовать источник вообще, второе выбирает режим внутри платформы. Три
VK-сообщества (`doskanabali`, `zhilyo_abhaziya`, `moretut25`) активны, но
собираются только по комментариям: `posts_enabled: false`,
`comments_enabled: true`. Превращать их в обычный сбор постов нельзя.
| `notes` | нет | Заметки |

Для Telegram достаточно указать любой из вариантов: `example`, `@example`,
`t.me/example` или `https://t.me/example/123`. Реестр сам приводит запись к
username `example` и каноническому URL `https://t.me/example`.

Недопустимые Telegram-адреса реестр отвергает при загрузке, а не «угадывает»:
приватные приглашения (`t.me/+hash`, `t.me/joinchat/...`), чужие хосты
(`https://evil.com/t.me/x`), схема `tg://` и имена с недопустимыми символами
дают ошибку `SourceRegistryError`. Молчаливая догадка была бы опаснее ошибки:
она превратилась бы в канонический `https://t.me/<чужой-канал>`.

Неизвестные дополнительные поля (и у источника, и на верхнем уровне файла)
загрузчик игнорирует. Опечатка в названии поля не может тихо отключить
источник: отключает только явное `"enabled": false`.

### Платформы расширяемы, но платформа ≠ сборщик

Новое значение `platform` (`youtube`, `dzen`, что угодно) не требует изменений
Python-кода: загрузчик примет его и не упадёт.

**Но появление платформы в реестре само по себе не создаёт для неё сборщик.**
Это только запись о намерении наблюдать. Список платформ, для которых сбор
реально реализован в этом репозитории, — `IMPLEMENTED_COLLECTOR_PLATFORMS` в
`app/services/source_registry.py`; сейчас он **пуст**.

Известные платформы в `app/domain/sources.py` — это только константы и защита
от опечаток в тестах, а не перечень поддерживаемого сбора.

## Как код получает источники

```python
from app.services.source_registry import collection_targets

for source in collection_targets(platform="telegram"):
    ...  # source.target -> https://t.me/<username>
```

- `collection_targets(...)` — единственная точка входа для кода сбора.
- Возвращаются **только активные** источники: запись с `"enabled": false`
  не попадает в выборку никогда.
- Можно фильтровать по `platform` и по `source_type`.
- Возврат источника отсюда означает «должно собираться», а не «уже собирается».

Полный API — `app/services/source_registry.py`:
`load_registry()`, `SourceRegistry.all() / .enabled() / .disabled() / .get() /
.by_platform() / .by_source_type()`.

## Просмотр реестра

```powershell
.\.venv\Scripts\python.exe scripts\list_sources.py
.\.venv\Scripts\python.exe scripts\list_sources.py --platform telegram
```

Скрипт только читает и печатает. Он ничего не собирает, не ходит в сеть и не
меняет файлы. Полноценное управление источниками через интерфейс — отдельный
будущий этап.

## Границы текущего этапа

- Сам сбор данных живёт в отдельном проекте Travel Lead Radar. Control Center
  читает уже подготовленные сигналы из `leads.db` в read-only режиме.
- Реестр задаёт **что наблюдаем по замыслу**; он не запускает сбор сам по себе
  и ничего не мониторит.
- **Radar пока не читает этот реестр.** Он работает со своим
  `app/sources/sources.json`. Пока это так, правка `config/sources.json` не
  меняет реальный сбор.
- Интеграция реестра с Travel Lead Radar — отдельный следующий этап: путь к
  реестру через переменную окружения, адаптер формата, пропуск платформ без
  сборщика, проверка паритета в dry-run и только затем переключение.
- Админки и UI управления источниками сейчас нет — это отдельный этап.
