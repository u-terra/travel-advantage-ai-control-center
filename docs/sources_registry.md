# Реестр источников

## Что такое источник

Источник — это **наблюдаемый** канал, за которым мы следим, чтобы находить:

- инфоповоды;
- темы для контента;
- рыночные сигналы;
- аргументы и возражения;
- истории и отзывы;
- идеи для сценариев общения.

Источник — это **не база знаний** и **не источник гарантированной истины**.
Публикации источника не копируются как готовый контент. На их основе создаётся
новый материал, который затем проходит обычную ручную проверку владельцем
(включая Safety Layer, если тема касается дохода, цен, скидок, тарифов, оплаты,
бронирования или доступности).

## Кто владелец реестра

**Control Center — владелец списка источников.** Здесь решается, какие источники
существуют и какие из них разрешены к использованию.

Travel Lead Radar в будущем станет только исполнителем: возьмёт активные
источники, посмотрит, для каких платформ у него есть сборщик, соберёт
публикации и сложит результат в свою `leads.db`.

> **Сейчас Radar ЕЩЁ НЕ читает этот файл.** Он продолжает работать со своим
> `app/sources/sources.json`. Переключение — отдельный следующий этап.

## Четыре разных состояния — не путать

Это самое важное место документа. Запись в реестре ≠ работающий мониторинг.

| Состояние | Что означает | Где проверяется | Сейчас |
|---|---|---|---|
| **Зарегистрирован** | Источник описан в активном реестре | `load_registry().all()` | 24 источника в стартовом наборе |
| **Активен** (`enabled`) | **Разрешение** использовать источник | `registry.enabled()`, `collection_targets()` | 18 из 24 |
| **Есть сборщик** | Реализовано чтение этой платформы | `IMPLEMENTED_COLLECTOR_PLATFORMS` | в этом репозитории **пусто** |
| **Реально мониторится** | Источник физически читается | Travel Lead Radar, по своему файлу | 16 (через файл Radar, не через этот реестр) |

Ключевое различие: `enabled` — это **разрешение**, а не факт. Активный источник
на платформе без сборщика просто не будет собираться. Реальный мониторинг
требует и разрешения, и сборщика для его платформы.

`collection_targets()` возвращает **список намерения**: «за этим мы хотим
наблюдать». Это не отчёт о том, что уже собирается.

## Где хранятся источники

Конкретные каналы **не зашиты** в Python — они живут в data-файлах. Файлов
два, и роли у них разные:

| Файл | Роль | Git | Деплой | Меняется во время работы |
|---|---|---|---|---|
| `config/sources.json` | **seed** — стартовый набор | отслеживается | переносится | **нет** |
| `data/sources.json` | **runtime** — рабочее состояние | игнорируется (`data/`) | не переносится | да |

Так сделано ради одного конкретного риска: файл не может быть одновременно
версионируемой частью поставки и изменяемым состоянием. Пока это был один
файл, деплой новой версии `config/sources.json` затёр бы источники, которые
владелец добавил через бота.

Путь рабочего файла переопределяется переменной `SOURCE_REGISTRY_PATH`
(по аналогии с `JOURNAL_DB_PATH`); по умолчанию — `data/sources.json`.

### Что происходит при первом запуске

1. приложение стартует, рабочего файла ещё нет;
2. `data/` создаётся при необходимости, и в него разворачивается копия seed;
3. дальше **источником истины является только рабочий файл**.

Существующий рабочий файл не перезаписывается никогда — ни при старте, ни при
обновлении seed. Обновлённый seed попадает к владельцу только через явный
сценарий восстановления (удалить рабочий файл и дать ему развернуться заново).

Пока рабочего файла нет, чтение идёт из seed — набор источников одинаковый
до и после разворачивания, поэтому UI и сбор не могут увидеть разные списки.
Само по себе чтение рабочий файл **не создаёт**: `scripts/list_sources.py` не
оставляет следов. Разворачивание делает приложение при старте и любая запись.

Чтобы добавить источник в поставку (для всех новых установок) — правится
seed. Чтобы добавить источник себе — бот или рабочий файл.

## Формат записи

Файл начинается с версии формата:

```json
{
  "schema_version": 2,
  "sources": [ ... ]
}
```

`schema_version` нужен, чтобы старый код не пытался прочитать файл нового
формата.

| Версия | Что означает |
|---|---|
| `1` | Базовый формат, блока `collector` нет |
| `2` | Добавлен необязательный `collector` (текущая версия) |

Обе версии читаются. Файл v1 остаётся валидным — у его источников просто
пустой `collector`. Неизвестная версия отклоняется с понятной ошибкой вместо
тихой неверной загрузки. Отсутствие поля трактуется как версия `1`. Блок
`collector` в файле, помеченном как v1, тоже отклоняется: иначе настройки
сборщика потерялись бы незаметно.

Сама запись источника:

```json
{
  "id": "telegram_example",
  "name": "@example",
  "platform": "telegram",
  "username": "example",
  "url": "https://t.me/example",
  "source_type": "monitored_source",
  "purpose": "content_and_business_signals",
  "enabled": true,
  "priority": 50,
  "notes": "Свободный комментарий",
  "collector": { "fetch_limit": 3 }
}
```

| Поле | Обязательно | Описание |
|---|---|---|
| `id` | да | Уникальный технический идентификатор |
| `name` | да | Человекочитаемое имя |
| `platform` | да | `telegram`, `vk`, `rss`, `web` — список расширяемый |
| `url` / `username` | да (одно из) | Адрес источника |
| `source_type` | да | Категория/роль: `monitored_source`, `community_comments`, `reviews_and_stories`, `own_web_resource`, … |
| `purpose` | да | Для чего наблюдаем источник |
| `enabled` | нет (по умолчанию `true`) | Разрешение использовать источник. `false` — в сбор не попадает никогда |
| `priority` | нет (по умолчанию `50`) | Меньше число — выше приоритет |
| `notes` | нет | Заметки |
| `created_at` | нет | Когда источник заведён (UTC ISO-8601) |
| `updated_at` | нет | Когда его последний раз меняли |
| `collector` | нет (с v2) | Настройки конкретного сборщика — см. ниже |

Отметки времени проставляются автоматически при добавлении и изменении через
Control Center. У источников, заведённых раньше, они пустые: задним числом
даты не выдумываются. Эти два поля намеренно **не** привязаны к
`schema_version` — читатель, который о них не знает, просто их игнорирует, и
поведение сбора от этого не меняется (в отличие от `collector`, где потеря
настройки изменила бы режим работы).

### `platform` и `source_type` — разные вещи

Это место, где легко ошибиться при миграции. В Travel Lead Radar поле с именем
`source_type` означает **платформу** (`rss`/`vk`/`telegram`). В Control Center
это не так:

| Смысл | Control Center | Travel Lead Radar |
|---|---|---|
| Платформа | `platform` | `source_type` |
| Роль источника | `source_type` | — |
| Режим анализа | `collector.analysis_profile` | `analysis_profile` |

Значение Radar `source_type` переносится в `platform`, а **не** в одноимённое
поле Control Center. `analysis_profile` (`publisher` / `user_comment`) хранится
как настройка сборщика и никогда не маскируется под `source_type`.

### Блок `collector`

Всё, что нужно только конкретному сборщику, живёт отдельно от общих свойств
источника:

```json
"collector": {
  "analysis_profile": "user_comment",
  "posts_enabled": false,
  "comments_enabled": true,
  "vk_screen_name": "example",
  "vk_group_id": null,
  "fetch_limit": 3,
  "min_score_for_llm": 70,
  "language": "ru"
}
```

Реестр **не толкует смысл** этих настроек — он только проверяет типы известных
ключей, чтобы поле не поменяло смысл молча (строка `"false"` в булевом флаге
дала бы `True` и включила сбор там, где его выключали). Неизвестные ключи
сохраняются нетронутыми: их поймёт сборщик своей платформы.

| Ключ | Тип | Смысл |
|---|---|---|
| `analysis_profile` | строка | `publisher` или `user_comment` |
| `posts_enabled` | булев | Собирать посты сообщества |
| `comments_enabled` | булев | Собирать публичные комментарии |
| `drop_promo` | булев | Отбрасывать промо-посты (Telegram) |
| `fetch_limit` | число ≥ 0 | Сколько свежих публикаций брать |
| `min_score_for_llm` | число ≥ 0 | Порог передачи в LLM-анализ |
| `vk_screen_name` | строка | Короткое имя VK-сообщества |
| `vk_group_id` | число или `null` | Числовой ID VK-сообщества |
| `language` | строка | Язык источника (Radar печатает его в консоли) |

`enabled` и `collector.posts_enabled` — **разные вещи**. Первое разрешает
использовать источник вообще, второе выбирает режим внутри платформы. Три
VK-сообщества (`doskanabali`, `zhilyo_abhaziya`, `moretut25`) активны, но
собираются только по комментариям: `posts_enabled: false`,
`comments_enabled: true`. Превращать их в обычный сбор постов нельзя.
| `notes` | нет | Заметки |

Для Telegram достаточно указать любой из вариантов: `example`, `@example`,
`t.me/example` или `https://t.me/example/123`. Реестр сам приводит запись к
username `example` и каноническому URL `https://t.me/example`.

Недопустимые Telegram-адреса реестр отвергает при загрузке, а не «угадывает»:
приватные приглашения (`t.me/+hash`, `t.me/joinchat/...`), чужие хосты
(`https://evil.com/t.me/x`), схема `tg://` и имена с недопустимыми символами
дают ошибку `SourceRegistryError`. Молчаливая догадка была бы опаснее ошибки:
она превратилась бы в канонический `https://t.me/<чужой-канал>`.

Неизвестные дополнительные поля (и у источника, и на верхнем уровне файла)
загрузчик игнорирует. Опечатка в названии поля не может тихо отключить
источник: отключает только явное `"enabled": false`.

### Платформы расширяемы, но платформа ≠ сборщик

Новое значение `platform` (`youtube`, `dzen`, что угодно) не требует изменений
Python-кода: загрузчик примет его и не упадёт.

**Но появление платформы в реестре само по себе не создаёт для неё сборщик.**
Это только запись о намерении наблюдать. Список платформ, для которых сбор
реально реализован в этом репозитории, — `IMPLEMENTED_COLLECTOR_PLATFORMS` в
`app/services/source_registry.py`; сейчас он **пуст**.

Известные платформы в `app/domain/sources.py` — это только константы и защита
от опечаток в тестах, а не перечень поддерживаемого сбора.

## Как код получает источники

```python
from app.services.source_registry import collection_targets

for source in collection_targets(platform="telegram"):
    ...  # source.target -> https://t.me/<username>
```

- `collection_targets(...)` — единственная точка входа для кода сбора.
- Возвращаются **только активные** источники: запись с `"enabled": false`
  не попадает в выборку никогда.
- Можно фильтровать по `platform` и по `source_type`.
- Возврат источника отсюда означает «должно собираться», а не «уже собирается».

Полный API — `app/services/source_registry.py`:
`load_registry()`, `SourceRegistry.all() / .enabled() / .disabled() / .get() /
.by_platform() / .by_source_type()`.

## Просмотр реестра

```powershell
.\.venv\Scripts\python.exe scripts\list_sources.py
.\.venv\Scripts\python.exe scripts\list_sources.py --platform telegram
```

Скрипт только читает и печатает. Он ничего не собирает, не ходит в сеть и не
меняет файлы.

## Управление источниками

Изменяется всегда рабочий файл (`data/sources.json`), и способа два —
руками или через Control Center. Результат одинаковый: тот же файл, тот же
формат.

### Раздел «📚 Источники» в боте

Доступен при включённом меню v2 (`TA_CONTROL_CENTER_V2_MENU_ENABLED=true`).
Показывает список с отметками 🟢 (разрешён) и ⚪️ (выключен), позволяет
переключать состояние нажатием и добавлять источник по ссылке.

Экран ничего не открывает и не скачивает: присланный адрес только
разбирается как строка.

### Программный доступ

```python
from app.services.source_registry_store import SourceRegistryStore

store = SourceRegistryStore()          # data/sources.json, seed — config/
store.ensure_bootstrapped()            # идемпотентно; зовётся при старте
store.list(platform="telegram")
store.add("https://t.me/example")      # или "@example"
store.toggle("telegram_example")
store.disable("telegram_example")
store.enable("telegram_example")
store.remove("telegram_example")       # редкий сценарий, см. ниже
```

`SourceRegistryStore` — **единственное** место, которое реестр изменяет.
Загрузка (`load_registry`, `collection_targets`) остаётся read-only и без
явного пути читает активный реестр — тот же, что видит бот.

Запись атомарная: файл сначала проверяется целиком в памяти и только потом
заменяется на диске. Сломанный реестр на диск не попадает, а неизвестные поля
и комментарии верхнего уровня сохраняются нетронутыми.

### Одновременные изменения

`os.replace` защищает от **повреждённого** файла, но не от **потерянного
обновления**: два потока могли бы прочитать одно состояние и записать разные
результаты, и второй перекрыл бы первого.

Поэтому блокировка держится на всём цикле «прочитали → изменили → записали»,
а не вокруг одной записи. Блокировка привязана к файлу, а не к объекту
магазина: хендлеры бота работают в разных потоках (`asyncio.to_thread`) и
могут создавать свои экземпляры.

По той же причине переключение — отдельная операция `toggle()`. Если бы
вызывающий читал состояние и записывал обратное, два быстрых нажатия отменили
бы друг друга.

Защита процесс-локальная. Приложение — один процесс (`python -m app`,
long-polling), поэтому её достаточно. Внешние файловые блокировки, Redis и БД
на этом этапе намеренно не вводятся. Правка рабочего файла руками во время
работы бота остаётся вне этой защиты — делать это стоит при остановленном
сервисе.

### Выключить, а не удалить

Обычный сценарий — `disable()`. Выключенный источник сохраняет историю решения
«сюда мы уже смотрели» и в сбор не попадает никогда. `remove()` эту историю
теряет, поэтому он второстепенный.

### Что принимается как адрес

| Ввод | Результат |
|---|---|
| `@example`, `t.me/example`, `https://t.me/example/42` | Telegram, username `example`, URL `https://t.me/example` |
| `https://example.com/blog` | `web` |
| `https://vk.com/example` | `vk` |
| `example.com` (без схемы) | отклоняется |
| `ftp://`, `file://`, `javascript:`, `tg://` | отклоняется |
| `https://user:pass@example.com` | отклоняется — секретам в реестре не место |
| `https://t.me/+hash`, `t.me/joinchat/...` | отклоняется — не публичный канал |

Схема для обычных сайтов обязательна: подставлять её за владельца значило бы
записать в реестр не тот адрес, который он дал. Для Telegram короткая форма
допустима — она однозначна.

### Дубликаты

Адрес приводится к каноническому виду (регистр хоста, хвостовой слеш, форма
Telegram-ссылки), и по нему ищется совпадение. Повторное добавление **не
создаёт вторую запись**: возвращается ошибка с уже существующим источником и
его состоянием. Один и тот же канал, присланный как `@example` и как
`https://t.me/example/42`, — это один источник.

Два **активных** источника с одним адресом реестр не читает вообще: это ошибка
файла, иначе получился бы двойной сбор и двойной счёт сигналов. Выключенная
копия рядом с активной допустима — так живут кандидаты.

### Что реестр НЕ хранит

Токены, ключи и пароли. Пользовательские данные. Собранные публикации.
Только описание источника.

## Content Intelligence — пока только словарь

`app/domain/content_intelligence.py` фиксирует, как в будущем будет
описываться материал из источника. Это **контракт, а не pipeline**: модуль
ничего не запускает, никуда не ходит и не вызывает LLM.

| Род материала | Предлагаемое действие по умолчанию |
|---|---|
| `news` | `generate_topics` |
| `post_idea` | `make_post` |
| `script_idea` | `make_script` |
| `case_or_review` | `adapt_for_travel_advantage` |
| `competitor_signal` | `observe` |
| `noise` | `skip` |

Полный список действий: `make_post`, `make_script`, `generate_topics`,
`adapt_for_travel_advantage`, `observe`, `skip`.

Действие — **предложение владельцу**, а не команда. Незнакомый род материала
даёт `observe`: наблюдать безопаснее, чем обрабатывать то, что система не
поняла.

Классификация подключена к существующему контракту разбора как необязательное
поле `SourceAnalysisPayload.classification`. Дубликата контракта не появилось,
адаптеры провайдеров не переписывались.

## Границы текущего этапа

- Сам сбор данных живёт в отдельном проекте Travel Lead Radar. Control Center
  читает уже подготовленные сигналы из `leads.db` в read-only режиме.
- Реестр задаёт **что наблюдаем по замыслу**; он не запускает сбор сам по себе
  и ничего не мониторит.
- **Radar пока не читает этот реестр.** Он работает со своим
  `app/sources/sources.json`. Пока это так, правка реестра не меняет
  реальный сбор.
- Интеграция реестра с Travel Lead Radar — отдельный следующий этап: путь к
  реестру через переменную окружения, адаптер формата, пропуск платформ без
  сборщика, проверка паритета в dry-run и только затем переключение.
- Автоматического чтения Telegram нет. Добавление канала в реестр не начинает
  его читать и не обходит никаких ограничений Telegram.
- Content Intelligence — только словарь значений. Классификация материалов
  ещё нигде не вычисляется.
- Фонового мониторинга и автоматической публикации нет.
